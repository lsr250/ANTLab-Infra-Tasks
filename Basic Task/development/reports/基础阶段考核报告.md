# 基础阶段考核报告

## 一、场景说明

模拟一个 **8 人小型工作室**，同时存在邮件整理、会议纪要、制度问答、代码审查和代码编写需求。服务部署在 WSL 2 + RTX 5060 上，通过 llama-server 提供本地推理。

- 办公任务：编程任务比例约 6:4
- 请求长度：单条最长约 2.3k tokens
- 输出上限：1024 tokens
- 到达方式：串行或最多 10 并发

## 二、实现

### 模型与硬件

| 项 | 值 |
|----|-----|
| GPU | NVIDIA RTX 5060 Laptop (8GB) |
| CUDA | 13.3 |
| 引擎 | llama.cpp (sm_120) |
| 模型 | Qwen2.5-3B-Instruct |
| 量化 | Q4_K_M (2.0 GB) |
| KV | f16（基线）/ q8_0（优化） |

### 系统模块

| 模块 | 位置 |
|------|------|
| 测试脚本 | src/benchmark/benchmark.py |
| 服务恢复 | src/recovery/watchdog.py |
| 前端 | src/frontend/app.py + templates/index.html |
| 配置 | configs/ |
| 结果 | results/baseline/ 和 results/optimized/ |

### 前端功能
- 显示服务健康状态（5 秒轮询）
- 展示测试配置（baseline / optimized 切换）
- 展示每个任务的 TTFT、TPOT、E2E、Token 数和输出预览
- 数据来源为 results/ 下的 JSONL 原始记录

### 服务恢复
- watchdog 每 5 秒轮询 /health
- 检测失败后自动 pkill + 重启
- 重启后等待 /health 返回正常，确认就绪
- 记录异常时间、恢复时间和耗时

## 三、测试

### 基线配置（KV f16）

-c 65536 -np 4 -ctk f16 -ctv f16
n_ctx_slot = 16384
显存：4350 MiB

| 并发 | 吞吐 (t/s) | TTFT (s) |
|------|-----------|----------|
| 1 | 105~108 | 0.046~0.179 |
| 4 | 220~270 | 0.219~0.322 |

### 优化配置（KV q8_0）

-c 65536 -np 4 -ctk q8_0 -ctv q8_0
n_ctx_slot = 16384
显存：3278 MiB（省 1072 MiB）

| 并发 | 吞吐 (t/s) | TTFT (s) |
|------|-----------|----------|
| 1 | 98~103 | 0.045~0.181 |
| 4 | 180~230 | 0.162~0.318 |

### 优化容量验证

将 -c 提升至 131072：

-c 131072 -np 4 -ctk q8_0 -ctv q8_0
n_ctx_slot = 32768（容量翻倍）
显存：4582 MiB

**结论**：KV q8_0 在几乎不损失吞吐的情况下，节省 25% 显存，并将可用上下文容量从 16384 翻倍到 32768。

## 五、服务恢复

- 故意 pkill llama-server
- watchdog 在 5 秒内检测到异常
- 自动重启后，2 秒内 /health 恢复正常
- 恢复后发请求，推理功能正常
